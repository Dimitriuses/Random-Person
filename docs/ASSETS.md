# Assets

## What ships today

`src/assets/avatars/` — seven SVG placeholder avatars, 360–363 bytes each:

| File | Used for |
|---|---|
| `male-child.svg`, `male-adult.svg`, `male-senior.svg` | `gender === 'Male'`, ages `<20` / `<50` / `50+` |
| `female-child.svg`, `female-adult.svg`, `female-senior.svg` | `gender === 'Female'`, same three bands |
| `unspecified.svg` | every other gender value — the bucket the 2019 code had no branch for |

All seven are generated by [`tools/build-avatars.js`](../tools/build-avatars.js) in
this repository and are covered by the repository's MIT licence. They are
deliberately abstract geometric badges: hue carries which gender group the
service bucketed the person into, lightness carries the age band, and nothing
else about a person is depicted. Regenerate with:

```bash
node tools/build-avatars.js
```

`src/favicon.ico` is the unmodified Angular CLI 8 default.

**The app makes zero third-party requests.** Measured on the built site with a
scripted session that generates people and opens each one's detail panel: the
2019 build contacted **7** external hosts (the Mockaroo endpoint plus all six
image hosts), the current build contacts **0**, with 0 failed requests and 0
console errors.

## What used to ship, and why it could not stay

The 2019 version hardcoded six image URLs in `person.service.ts` and hotlinked
them straight into the detail panel. Checked on 2026-07-30:

| Bucket | 2019 URL host | Status today |
|---|---|---|
| Male `<20` | `cdn170.picsart.com` | 200 |
| Male `<50` | `i.pinimg.com` | 200 |
| Male `<100` | `a.rgbimg.com` | 200 |
| Female `<20` | `www.nicepng.com` | **403** |
| Female `<50` | `photy.org` | **404** |
| Female `<100` | `images-na.ssl-images-amazon.com` | 200 |

Two problems, either of which is enough on its own:

1. **Two of the six were already dead**, so a third of the people the app
   generated rendered a broken image. Confirmed in the browser as well as by
   `curl` — `photy.org` fails with `net::ERR_BLOCKED_BY_ORB`.
2. **There was never any licence to use them.** They are photographs and
   illustrations of people, scraped from six unrelated websites — a stock-photo
   aggregator, a Pinterest CDN, a free-photo site, a clip-art site, a photo
   host, and an Amazon product image. A public repository plus a GitHub Pages
   demo both *redistribute* every file they serve, and hotlinking additionally
   spends someone else's bandwidth. None of that is curable by an attribution
   line.

So they were replaced rather than credited. Nothing from the 2019 set remains in
the repository, and because they were only ever URLs in a string literal, no
image file ever had to be deleted — the URLs are preserved in the
`v0.1-original` tag and in `git log`.

## The Mockaroo API key

Not an asset, but the same class of problem, and recorded here for completeness.
`person.service.ts` hardcoded a Mockaroo API key into the fetch URL. It was
public in this repository from 2019-10-23 and **still returned live data when
tested in 2026**. It has been removed from the source and revoked at the account.

Removing it from the working tree does not remove it from history — it is in five
commits and in the `v0.1-original` tag, which is why revoking it at the source
was the actual fix rather than a history rewrite. Rewriting those commits would
not have undone seven years of public exposure, and it would have destroyed the
preserved original.

## The schema the generator replaced

The 2019 URL pointed at a **saved schema** on the owner's Mockaroo account
(`person__default_.json`), so the API key on its own was never enough to
reproduce it — the schema had to exist too. It no longer does.

Recorded here so the historical contract is not lost. Measured from one 200-row
sample taken before the endpoint was retired:

| Field | Type | Observed |
|---|---|---|
| `first_name` | first name | — |
| `last_name` | last name | — |
| `fater_name` | first name | misspelled in the schema itself, which is why the 2019 model called it `faterName` |
| `gender` | gender | **8 distinct values** — `Male` 100, `Female` 82, `Genderqueer` 5, `Non-binary` 4, `Agender` 4, `Bigender` 2, `Genderfluid` 2, `Polygender` 1 |
| `year` | number | integers, **10–100 inclusive** — despite the name it is an age, and the app labels it "Age" |
| `phone` | phone | `NNN-NNN-NNNN`, 200/200 |
| `email` | email address | local part derived from `last_name` in 193/200, across 162 distinct real domains |

Two details worth keeping. The gender list is the whole reason 18 of those 200
rows rendered a broken image: the app branched on two values out of eight. And
`year` reaching 100 *inclusive* is why the `year < 100` test dropped another
three.

One Mockaroo fingerprint, the same one noted for the `PassBackup` seed data:
**every email local part ends with its row index rendered in base 36** —
`lmanginot0`, `hkingescot1`, `shankinson2`, `cwoolway3` … `200/200`. It is a
reliable tell that a dataset is Mockaroo-generated rather than real.

`PersonService` now generates all seven fields locally, with the same eight
gender values and the same 1–100 age range, so the shape the components consume
is unchanged. **There is deliberately no way to point the app back at Mockaroo.**
Restoring that would mean shipping a field that puts a live third-party
credential into a client-side bundle, and it would still require the reader to
recreate the schema above on their own account before a single button worked.
